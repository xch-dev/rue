# Rue

[![crate](https://img.shields.io/crates/v/rue-cli.svg)](https://crates.io/crates/rue-cli)
[![build](https://github.com/xch-dev/rue/actions/workflows/build.yml/badge.svg)](https://github.com/xch-dev/rue/actions/workflows/build.yml)
[![license](https://img.shields.io/badge/license-Apache--2.0-blue.svg)](LICENSE)

Rue is a statically typed programming language that compiles to [CLVM](https://chialisp.com/clvm) bytecode. It's designed as an alternative to [Chialisp](https://chialisp.com) for writing coin puzzles on the [Chia blockchain](https://chia.net).

[**Docs**](https://rue-lang.com) · [**Playground**](https://play.rue-lang.com) · [**Discord**](https://discord.gg/sagewallet)

```rs
fn main(public_key: PublicKey, conditions: List<Condition>) -> List<Condition> {
    let agg_sig = AggSigMe { public_key, message: tree_hash(conditions) };
    [agg_sig, ...conditions]
}
```

## Highlights

- **Type safe:** Structs, generics, type guards, and flow-sensitive narrowing catch entire classes of mistakes at compile time, before a puzzle ever touches the chain.
- **Optimized:** The compiler works hard to minimize the size and runtime cost of the generated bytecode.
- **Familiar:** A simplified, Rust-like syntax that feels more at home for most developers than Lisp.
- **Batteries included:** A standard library with conditions, tree hashing, currying, singletons, offers, and more.
- **Tooling:** A built-in test runner, formatter, CLVM debugger, and language server.

## Installation

Install the CLI from [crates.io](https://crates.io/crates/rue-cli):

```bash
cargo install rue-cli
```

See the [Installation](https://rue-lang.com/docs/installation) page for more options. If you just want to try the language, the [Playground](https://play.rue-lang.com) runs entirely in your browser.

## Quick Start

Create a new project:

```bash
rue init my-project
cd my-project
```

This creates a `Rue.toml` manifest and a `puzzles/main.rue` entrypoint:

```rs
fn main() -> String {
    "Hello, world!"
}
```

Compile it to CLVM:

```bash
$ rue build
(q . "Hello, world!")
```

## Modules and Paths

Every `.rue` file in a project is a module, every directory is a module containing its files and directories, and `mod name { ... }` declares a module inside a file. A path names an item in another module, such as `utils::greet`, and can start with:

- **A name in scope:** a file sees the other files and directories next to it by name, while an inline module only sees its own items, its imports and the prelude.
- **`super`:** from an inline module, the module it's in. From a file, the parent of the file's directory (since the file already sees its own directory's contents by name). Each further `super` goes up one more module.
- **`project`:** the module that the project's `entrypoint` in `Rue.toml` points to (such as the `puzzles` directory), from anywhere in the project. For a single file compiled on its own, that's the file itself. The standard library is its own project, so `project` in it names its own directory. `project` is a keyword, only allowed at the start of a path, and since the project's module has no parent, `super` can't follow it.

`super` and `project` name a module that contains the code, so its private items can be used, and `import project::*` brings them all in (like `import super::*`). Past that, the usual rules apply: an item inside another module (including a file reached through `project`) has to be exported. `export project::...` re-exports an item, like any other import path:

```rs
// puzzles/conditions/create.rue, where `project` and `super` both name `puzzles`
import project::utils::greet;

export fn hello() -> String {
    greet(project::main::NAME) + greet(super::main::NAME)
}
```

The [Modules](https://rue-lang.com/docs/modules) page covers modules, imports and exports in more detail.

## CLI

| Command                         | Description                                                            |
| ------------------------------- | ---------------------------------------------------------------------- |
| `rue init [path]`               | Create a new project with a `Rue.toml` manifest.                       |
| `rue build [file]`              | Compile the project (or a single file) and print the CLVM output.      |
| `rue test [file]`               | Run every `test fn` in the project (or a single file).                 |
| `rue fmt [paths...] [--check]`  | Format Rue source files, or check that they're already formatted.      |
| `rue debug <program> [solution]`| Run a CLVM program against a solution and print the result.            |
| `rue lints`                     | List every lint and its default level, and the lint groups.            |

Useful `build` flags:

- `--export <name>` - compile a specific exported function instead of `main`
- `--hex` - output serialized bytecode as hex
- `--hash` - output the tree hash of the compiled program
- `--debug` - include debug information such as assertion messages
- `--hard-fork-2` - target mainnet as it will be after hard fork 2 (see [Hard Fork 2](#hard-fork-2)); `test` and `debug` take it too
- `--operand-limits` - target CLVM with the `LIMITS` flag that mainnet enforces today (see [Operand Limits](#operand-limits)); `test` and `debug` take it too
- `--all` - compile every export in the project and write each one to a file (next to its source, or in `dist_dir` if set in `Rue.toml`)
- `--debug-metadata` - also write a debug metadata sidecar for each program (`<name>.rue.debug.clvm.bin`, in Chialisp's structural debug metadata format), which debuggers use to show where in the source a failing program was. It's written next to each program with `--all`, and otherwise next to the source file, or to `--debug-metadata=<path>`. The programs are the same either way

`test` and `debug` stop a program once its cost passes 11,000,000,000 (the same as Chia's block cost limit), so a program that never ends fails instead of hanging. `--max-cost <cost>` changes the limit.

When a test fails, `test` shows where it was in the source: the stack of calls that led to the failure, with the values of their parameters. `debug` does the same for a program built with `--debug-metadata` when it's given the sidecar with `--debug-metadata <path>` (which can be repeated, for programs that run other programs).

## Hard Fork 2

By default, Rue targets Chia mainnet as it is today, before hard fork 2. Turn on `hard_fork_2` in `Rue.toml`, or pass `--hard-fork-2` to `build`, `test` or `debug`, to target mainnet as it will be once hard fork 2 activates:

```toml
[compiler]
hard_fork_2 = true
```

| | Without `hard_fork_2` (default) | With `hard_fork_2` |
| --- | --- | --- |
| `modpow` | An error, since mainnet disables it until hard fork 2 | Allowed |
| `keccak256`, `keccak256_inline` | An error, since mainnet doesn't know the operator outside of the softfork guard until hard fork 2 | Allowed |
| Cost model, for running programs and for the optimizer's cost comparisons | The current one | The new one |
| `secp256k1_verify`, `secp256r1_verify` | The four byte opcodes that encode their cost | The one byte opcodes 64 and 65 |
| `LIMITS` | Only with `operand_limits` (see [Operand Limits](#operand-limits)) | Removed, so `operand_limits` can't be set with `hard_fork_2` |

`keccak256` can't be used inside the softfork guard instead, since the guard always returns nil, so a hash can't be returned from it.

Turning `hard_fork_2` on changes the compiled program, and so its puzzle hash, for any program that uses the secp operators. It can also change what the optimizer emits elsewhere, since it folds constants by comparing costs in the target's cost model.

`rue test`, and `rue debug` when it's run inside the project, run programs with the flags for the target, so tests behave as mainnet would at the target. Without `hard_fork_2`, a raw program run by `rue debug` fails on `keccak256` as it would on mainnet. It can still use `modpow`, unless `operand_limits` is on: mainnet disables `modpow` with the `DISABLE_OP` flag, which also limits the dividend of `/`, `%` and `divmod` to 2048 bytes, and Rue only applies operand length limits with `operand_limits`. Compiled programs can't use `modpow` either way, since the compiler rejects it. A program compiled with `hard_fork_2` can still fail on mainnet until hard fork 2 activates, and the costs reported for it don't match mainnet's until then. Const expressions are evaluated at compile time with the target's cost model, which `const_eval_max_cost` is measured in.

## Operand Limits

Chia mainnet runs programs with CLVM's `LIMITS` flag until hard fork 2, which makes some operators fail when an operand is too long (counting any leading zero bytes):

| Operator                       | Fails when                                                                                   |
| ------------------------------ | -------------------------------------------------------------------------------------------- |
| `*`                            | an operand is longer than 256 bytes, or the running product grows past 1024 bytes            |
| `/`, `%`, `divmod`             | the dividend is longer than 256 bytes, or the divisor is longer than 1024 bytes              |
| `modpow`                       | the base, exponent or modulus is longer than 256 bytes                                       |
| `g1_multiply`, `g2_multiply`   | the scalar is longer than 1024 bytes                                                         |

By default, Rue doesn't apply `LIMITS`, even though it targets mainnet before hard fork 2 otherwise (see [Hard Fork 2](#hard-fork-2)). To target CLVM with `LIMITS`, turn on `operand_limits` in `Rue.toml`, or pass `--operand-limits` to `build`, `test` or `debug`. It can't be set with `hard_fork_2`, since hard fork 2 removes `LIMITS`:

```toml
[compiler]
operand_limits = true
```

With `operand_limits`:

- A release build fails under `LIMITS` exactly when the debug build does. `*`, `/`, `%` and `divmod` are treated as able to fail unless every operand is a short enough constant (and the divisor isn't zero), so they're never dropped or moved into a branch, and no optimization removes or adds a failure caused by an operand's length. For example, `x % 2 == 1` keeps its `%`, rather than checking the low bit with `logand`, which doesn't limit `x`.
- Lints that ask whether a value can fail, such as `inline_value_may_fail`, count these operators as able to fail.
- `rue test` runs tests with `LIMITS`, so a test fails where mainnet would, and so does `rue debug` when it's run inside the project (from its directory or any directory below it). Outside of a project, `rue debug --operand-limits` runs a program with `LIMITS`.

Without it, operands of any length are treated as allowed, so `*` can't fail and `/`, `%` and `divmod` only fail for a zero divisor. A program compiled this way can pass its tests and succeed in debug builds, yet fail on mainnet today when an operand is longer than a limit. The optimizer can also change whether a release build fails under `LIMITS`, in either direction:

- It can remove a failure, such as by compiling `x % 2 == 1` to `logand`, or by dropping or moving a product or quotient it treats as unable to fail, so the release build succeeds where the debug build fails.
- It can add one, by folding constants into an operand longer than a limit, even when each constant in the source is within the limits. For example, `x * C * C` with a 150 byte constant `C` becomes `x` times one 299 byte constant, so the release build fails where the debug build succeeds. It also flattens products and moves their constants to the end, which changes the running products that `LIMITS` checks: `a * 0 * b * c * d * e` becomes `(* a b c d e 0)`, whose running product can grow past 1024 bytes before it reaches the zero.

For solutions whose values match their declared types, the only failures the optimizer removes are the length checks of `LIMITS` itself, never an `assert` or `raise`, and the release build returns what the source computes without `LIMITS`. So leaving the option off never makes a release build accept such a spend that the source rejects. (A value that doesn't match its type, such as a pair passed for an `Int`, can make a release build succeed where the debug build fails with or without the option, since Rue trusts declared types and doesn't check them at runtime.) The risk is the other way: a spend can fail on mainnet although its tests pass, and if the long operand is fixed by the puzzle (such as a constant or a curried value), that path can't be spent at all.

So a program compiled without the option is safe to run on mainnet today as long as no operand or product of these operators can come near the limits, counting the values the program computes, the constants the optimizer folds together, and the products of operands it multiplies together. Typical puzzles are far from them: amounts are at most 8 bytes and hashes are 32. Turn the option on when operands could be that long, or to make release and debug builds agree exactly under `LIMITS`.

Either way, `const` expressions are evaluated at compile time without `LIMITS`, since they're never run on chain, so they can use operands of any length.

## Lints

Warnings such as unused bindings or unnecessary casts are lints, which can be configured to be allowed, reported as warnings, denied (which fails compilation), or forbidden (which is like denied, but can't be changed by attributes or later flags). Run `rue lints` to see every lint and its default level.

Related lints are also in groups, which can be configured anywhere a lint can. Run `rue lints` to see the lints in each group:

- `unused` contains every `unused_*` lint.
- `style` contains lints for code that works, but could be written more simply, such as `unnecessary_parens` and `collapsible_if`.
- `suspicious` contains lints for code that's likely to be a mistake, such as `self_comparison` and `unconditional_recursion`.

A group sets the level of every lint in it, including the ones that are allowed by default, so `style = "warn"` also enables `negated_condition` and `shadowed_binding`.

Levels can be set in `Rue.toml`:

```toml
[lints]
unused = "deny"
unused_binding = "allow"
unnecessary_cast = "allow"
```

Within `Rue.toml`, a lint's own level takes precedence over the level of its group, regardless of the order they're written in. Here every `unused_*` lint is denied, except for `unused_binding`. The exception is a forbidden group, whose lints can't be set to any other level, so `unused = "forbid"` with `unused_binding = "allow"` is an error.

Levels can also be overridden for a single `build` or `test` with `-A`/`--allow`, `-W`/`--warn`, `-D`/`--deny` and `-F`/`--forbid`, which take precedence over `Rue.toml`, including a group flag over a lint set individually in `Rue.toml`. Among the flags, a lint's own flag takes precedence over its group's, unless the group is forbidden. Otherwise, if a lint is passed more than once, the last flag wins, unless the lint is already forbidden in `Rue.toml` or by an earlier flag (which is an error):

```bash
rue build -D unused -A unused_import
```

Levels can also be set in the source code, with an `allow`, `warn`, `deny` or `forbid` attribute on an item (such as a function, constant, struct, type alias, import or module) or a statement. The attribute applies to everything inside of what it's attached to, and the innermost one takes precedence over any outer attributes and the project's levels, whether it names a lint or a group. If an item or statement has more than one attribute for the same lint, the last one wins:

```rs
#[deny(unused_binding)]
mod strict {
    #[allow(unused)]
    fn reserved(value: Int) -> Int {
        #[warn(unused_binding)]
        let unused = 1;
        42
    }
}
```

A `forbid` attribute works like `deny`, but nothing inside of it can change the lint's level. The same goes for lints forbidden in `Rue.toml` or on the command line. An attribute or flag that tries to change the level of a forbidden lint has no effect on it, and is reported as an error. A group still sets the lints in it that aren't forbidden:

```rs
#[forbid(unused_binding)]
fn strict() -> Int {
    #[allow(unused_binding)] // Error: Cannot set lint `unused_binding` to `allow`, since it's forbidden by the attribute on line 1
    let unused = 1;
    42
}
```

An `expect` attribute allows a lint like `allow` does, but also expects it to be reported inside of what it's attached to. If it never is, the attribute is reported with the `unfulfilled_lint_expectation` lint, so it doesn't stay around after the code it was written for changes. An `expect` for a group is fulfilled by any lint in it, and like `allow`, it can't change a forbidden lint. As in Rust, expectations aren't checked if there are any errors other than lints (since code that doesn't compile can't be fully linted), and `unfulfilled_lint_expectation` itself can't be expected:

```rs
fn main() -> Int {
    #[expect(unused_binding)]
    let unused = 1;
    42
}
```

To set a level for a whole file, use an inner attribute (with a `!`) at the start of the file, before any items. Inner attributes can also go at the start of a `mod { ... }` body to apply to the whole module, where they come after the attributes on the `mod` itself, so they take precedence unless those forbid the lint. Attributes on the items inside still override them:

```rs
#![allow(unused_function)]

fn reserved() -> Int {
    0
}

#[warn(unused_function)]
fn checked() -> Int {
    1
}
```

## Testing

Tests are just functions marked with `test`, and they live right alongside your code:

```rs
fn factorial(num: Int) -> Int {
    if num > 1 {
        num * factorial(num - 1)
    } else {
        1
    }
}

test fn factorial_works() {
    assert factorial(0) == 1;
    assert factorial(5) == 120;
}
```

```bash
rue test
```

## Contributing

Contributions are welcome! The project builds with a stable Rust toolchain (pinned in [`rust-toolchain.toml`](rust-toolchain.toml)).

```bash
# Run the full test suite, which also checks the snapshots without changing them
cargo test --workspace

# Check the .yaml snapshots, std_tests.yaml and the formatting of the .rue files, printing what
# differs without changing any files (`-- --help` describes what's checked and the filter)
cargo run -p rue-tests --release -- [filter]

# Rewrite the snapshots, and reformat the .rue files, to match the current output
cargo run -p rue-tests --release -- --bless [filter]

# Lint and format
cargo clippy --workspace --all-targets
cargo fmt --all
cargo run -p rue-cli -- fmt 'examples/**/*.rue' 'tests/**/*.rue' 'crates/rue-compiler/src/std/**/*.rue'
```

Each test in `tests` and `examples` (a `.rue` file, or a directory of them) has a matching `.yaml` snapshot with its compiled output, runtime cost, and test results. Review snapshot diffs carefully, since they show exactly how a change affects the generated bytecode.

To run the playground locally:

```bash
cd wasm && pnpm install && pnpm build
cd ../playground && pnpm install && pnpm dev
```
